# context-pool-core — Benchmark Results — 2026-07-21

First benchmark for this package — no prior baseline to compare against.

```
tick() with 24 registered clients (budget=4): 5.52 µs/op
tick() with 100 registered clients (budget=4): 12.18 µs/op
tick() with 500 registered clients (budget=4): 22.62 µs/op

Baseline: naive "render everyone, always" loop
24 clients: 0.34 µs/op
100 clients: 0.30 µs/op
500 clients: 1.20 µs/op
```

## Notes

- `tick()` scales roughly linearly with registered client count (visibility check + sort of the visible subset), and stays well under a 16ms frame budget even at 500 registered clients (22.6 µs — about 0.14% of a 16ms frame).
- The "baseline" here isn't a faster equivalent to replace this package with — it's the naive pattern this package exists to prevent (the real carousel bug: one `WebGLRenderer` per canvas, no budget check at all). It's cheaper per-call only because it does zero of the bookkeeping that prevents context exhaustion; a real page running that baseline pattern would create N real WebGL contexts instead of the 1 this package's actual consumer (`ThreeContextAdapter`) needs. That cost isn't visible in a Node benchmark since there's no real GPU here — it's the entire reason this package exists.
- No industry-standard equivalent to benchmark against for the same reason as `render-budget-core`: this is a novel scheduling layer, not a drop-in replacement for a common pattern.
